# MoonVape v4 — аудит и отчёт о выполненных изменениях

## 0. Главное
1. **Ничего из SQL не запускалось.** Миграции 0019–0025 (≈2300 строк PL/pgSQL), `tests_v6.sql`, `pytest` и `npm run build` не выполнялись: в среде разработки нет PostgreSQL, Supabase, сети, `fastapi`, `pytest`, Next.js. Это самый большой риск релиза. Проект и до v4 никогда не запускался целиком (его README это прямо признаёт). Порядок безопасного запуска — `docs/DEPLOY_v4.md`: тестовая база → `tests_v6.sql` → только потом продакшен.
2. Что **реально выполнено** и прошло: статический анализ SQL; 34 offline-теста backend (на заглушках зависимостей; проверены мутациями); 9 тестов денег/периодов в Node; проверка типов TypeScript (с заглушками React). Подробно — `docs/TESTING_v4.md`.
3. Аудит нашёл **две критические уязвимости, не замеченные в прежнем отчёте** (раздел 2): анонимное чтение себестоимости и утечка себестоимости покупателю. Обе исправлены.
4. К продакшену не подключался, миграции на реальных данных не запускал.

## 1. Карта архитектуры (до v4)
`Telegram → Mini App (Next.js, Vercel) → FastAPI + aiogram (Render) → PostgREST/RPC → Supabase (PostgreSQL)`. Вся бизнес-логика — в `SECURITY DEFINER` функциях; backend проверяет `initData` Telegram и роль по таблице `admins`, дальше вызывает RPC с `service_role`.

## 3. Что реализовано по разделам ТЗ

### 3.1 Индивидуальные цены (раздел 2) — реализовано в коде, не запускалось
Таблица `customer_prices` (цена, примечание, срок, вкл/выкл, кто и когда). Единый расчёт `_pricing_for`: персональная → оптовая ступень → розница. Заказ от 50 шт. требует согласования только для позиций без персональной цены. В заказе сохраняется применённая цена, `price_source`, `reference_price`, `has_personal_price`. Старые заказы не пересчитываются. Изменять может только владелец; создание/изменение/отключение/удаление пишутся в `audit_log` со старым и новым значением; повтор без изменений аудит не плодит. Предупреждение «ниже себестоимости» — в ответе и в карточке клиента. Покупатель видит пометку «персональная цена» в корзине и заказе; владелец — 💎 в заказе; администратор города видит только итоговые цены.

### 3.2 München / Hannover (раздел 3) — реализовано в коде, не запускалось
`cities.finance_mode` (`owner_operated` | `city_managed`) хранится в БД; München по вашему указанию переведён в `owner_operated`, Hannover — `city_managed` (запись в `city_mode_history`). Для `owner_operated` `_settlement` возвращает «`München — управляется владельцем. Передача денег владельцу не требуется`», долг 0, а `record_cash_transfer` отклоняется на уровне БД. Выручка и прибыль считаются по обоим городам; фильтры сохранены; добавлена разбивка по городам. Остаток кассы München показывается отдельно.
**Модель денег.** Баланс счёта = стартовый остаток + выручка кассы города (считается из `orders`, не копируется — двойного учёта нет) + проводки `cash_entries`. Долг Hannover = остаток его кассы. На момент миграции стартовый остаток кассы Hannover = прежний долг (число не меняется). Смена режима: в `owner_operated` — только при нулевом остатке (`settle_first`); в `city_managed` — старая касса закрывается (деньги остаются у владельца), новая начинается с нуля: **искусственного долга не возникает**, исторические записи не меняются.

### 3.3 Закупки и FIFO (раздел 4)
Поставщики; закупка draft → posted; доставка и допрасходы распределяются по стоимости позиций (остаток копейки — в последнюю); партии с полной себестоимостью; оплата со счёта — движение денег, не расход; сторно закупки, пока партии не тронуты. Выдача заказа списывает партии по FIFO, пишет `batch_consumptions` и `order_items.cogs_total`; старые заказы продолжают считаться по снимку `unit_cost`. Существующие остатки превращены в «начальные» партии по `cost_price`. Инвариант «Σ партий = остаток» проверяется `inventory_batch_check`; при расхождении продажа не блокируется (партия достраивается, пишется аудит `fifo_self_heal`). Блокировки строк склада — в едином порядке по `id`.

### 3.4 Кассы и деньги (раздел 5)
Счета (кассы городов, банк владельца, свои), внесение/изъятие, переводы (пара проводок, не доход/расход), корректировки с причиной, сторно (в том числе перевода и проводки финансов), идемпотентность по ключам, запрет отрицательного баланса под блокировкой счёта, неизменяемый журнал.

### 3.5 Перемещения (раздел 6)
draft → «в пути» → получено / отмена. Отправка списывает по FIFO и запоминает слои себестоимости; получение создаёт партии с теми же ценой и датой; отмена в пути возвращает отправителю. Общая стоимость и число единиц сохраняются (учитывая «в пути»). Старый `admin_transfer_stock` сохранён как «создать+отправить+получить».

### 3.6 CRM и аналитика (разделы 7–8)
Список клиентов (поиск по имени/@username/Telegram ID, активные 30/90 дней, сортировки, пагинация, экспорт CSV), профиль (заказы, сумма, средний чек, последний заказ, персональные цены). Финансы: периоды (сегодня, вчера, 7/30 дней, месяц, прошлый месяц, произвольный), города, категории, товары, сравнение с предыдущим периодом, разбивка по городам, остатки по себестоимости и «в пути»; «Аналитика»: прибыльность товаров (маржа < 20 %, без продаж при наличии остатка), городов, остатков.

### 3.7 Журнал, безопасность, уведомления (разделы 9–10)
Единый журнал (`activity_feed`) объединяет аудит, склад, статусы и правки заказов, финансы, деньги. Аудируются: цены и персональные цены, товары/варианты/категории, остатки, закупки, перемещения, выдача/отмена заказов, режим города, переводы, корректировки, настройки, экспорты. Уведомления: низкие остатки (порог в настройках), дедупликация, журнал рассылок и статистика доставки, ошибки финансовых операций (аудит; при сбое БД — сообщение владельцу).

### 3.8 Интерфейс (раздел 11)
Разделы: Главная · Заказы · Склад · Товары (с оптовыми ценами и категориями) · Закупки · Перемещения · Клиенты · Финансы (Сводка/Счета/Журнал) · Взаиморасчёты · Аналитика · Настройки. Подтверждения на финансовых действиях, понятные сообщения об ошибках, деньги вводятся без `float`. **Визуально и на устройствах не проверялось.**

### 3.9 Юридическая проверка (раздел 12)
Код не обходит ограничения: рассылки выключены по умолчанию и требуют согласия; кнопка возраста не считается проверкой — добавлена опциональная проверка по документу при выдаче. Юридические вопросы — `docs/LEGAL_CHECKLIST.md`. **Это не заключение юриста.**

## 4. Архитектурные решения и их последствия
* Выручка не копируется в журнал денег, а выводится из заказов — исключает двойной учёт, но кассы городов считают продажи только с даты открытия счёта.
* `cash_transfers` заморожена: новые передачи идут через счета. Старые записи сохраняются и входят в стартовый остаток.
* 7-аргументная `finance_post_entry` удалена: для `cash_in/cash_out` теперь обязателен счёт. Backend v3 с базой v4 финансовые проводки не создаёт — выкладывайте backend сразу после миграций.
* Редактирование заказа покупателем пересчитывает **весь** заказ по ценам на момент правки (как и раньше — для ступеней); заказ без правки покупателя не меняется никогда.
* CRM и персональные цены — только владелец. Администратор Hannover не видит клиентов в CRM.
* Персональная цена — фиксированная, на товар целиком (все варианты); процентных скидок нет.

## 5. Нерешённые проблемы и риски
**Критичные (до продакшена)**
1. SQL-миграции и `tests_v6.sql` не запускались; вероятны опечатки/ошибки логики. Запуск — на тестовой базе (`DEPLOY_v4.md`).
2. Не проверено, что PostgREST принимает деньги строкой в `numeric`-параметры RPC (по моему знанию — да). Если нет — изменить `helpers.money`.
3. `pytest` и `npm run build` не запускались; валидация Pydantic (`decimal_places`) не проверена на реальных библиотеках. Старые экраны товаров/цен всё ещё шлют числа JS.
4. Параллельность проверена только рассуждением и блокировками; ручные сценарии — `TESTING_v4.md`.
5. Юридическая часть не пройдена; реальной проверки возраста нет; НДС в системе не рассчитывается.
**Функциональные ограничения**
6. Возвратов после выдачи нет (убраны в 0005); подготовленные формулы сторно не покрывают возврат товара.
7. Перемещение принимается целиком (частичного получения нет); создавать/отправлять/получать может только владелец.
8. `cost_price` товара не обновляется автоматически от закупок; предупреждение «ниже себестоимости» сравнивает с ним.
9. Начальные остатки касс München и банка = 0; владелец вносит их «Корректировкой».
10. Миграция 0021: заказ, оплаченный в секунды запуска, может не попасть ни в стартовый остаток, ни в кассу — запускайте без выдач.
11. Доставка уведомлений «минимум один раз»: при падении между отправкой и пометкой сообщение может уйти повторно через ~2 минуты.
12. Низкие остатки сообщаются после выдачи заказа, не после ручной корректировки.
13. Журнал действий показывает до 500 записей за выбранный период.
14. Сравнение периодов — только во «Финансы → Сводка».
**Качество**
15. Интерфейс не просматривался в браузере/Telegram; возможны недочёты вёрстки.
16. Offline-заглушки (`tests_offline/bootstrap.py`) могут разойтись с реальными библиотеками — они дополняют, а не заменяют `pytest`.
17. Старые `tests_v2/v4/v5` — «ворота» своих этапов и запускаются до 0019.
