## Как запускать
```bash
./scripts/run_checks.sh                       # всё, что не требует БД/сети
cd backend && pip install -r requirements.txt -r requirements-dev.txt && pytest -q     # настоящие тесты API
cd frontend && npm ci && npm run build        # сборка и проверка типов
# SQL: в тестовом проекте Supabase, после 0019–0025, SQL Editor → supabase/tests_v6.sql
```
Ожидаемый результат SQL-теста: `NOTICE: ALL V6 TESTS PASSED`. Ничего не сохраняется (rollback).

## Что покрывает `tests_v6.sql` (153 проверки) по списку из ТЗ
**Персональные цены:** клиент A получает персональную цену, клиент B — стандартную; A: персональная на один товар и оптовая ступень на другой; изменение персональной цены не меняет старый заказ; у `create_order` нет параметра цены; администратор города не может менять/читать персональные цены и CRM; цена ниже себестоимости даёт предупреждение; отключённая и истёкшая цены не применяются; аудит старого и нового значения; повтор без изменений не плодит аудит; ответ предпросмотра не содержит себестоимости.
**München:** продажа входит в общую выручку и валовую прибыль; долга перед владельцем нет; передача денег запрещена в БД (`transfer_not_required`); касса München считается отдельно и растёт от продаж; расход München уменьшает кассу и чистую прибыль; сумма по городам равна общей.
**Hannover:** выручка в долге; долг = остаток городской кассы; передача уменьшает долг; повтор с тем же ключом не списывает дважды; нельзя передать больше долга; история передач сохраняется; передача — не доход и не расход.
**Склад и закупки:** полная себестоимость партии (доставка распределяется по стоимости, остаток копейки — в последнюю позицию); закупка — не расход; FIFO списывает старые партии первыми; повторная выдача отклоняется, дубль списания невозможен (уникальный индекс); отмена заказа освобождает только резерв; нельзя продать больше свободного остатка; перемещение не меняет общую стоимость и число единиц; отмена в пути возвращает товар с прежней себестоимостью; ручное уменьшение остатка списывает партии; сторно закупки возможно, пока партии не проданы.
**Деньги и финансы:** перевод между счетами — не прибыль; идемпотентность; нельзя уйти в минус; сторно перевода и расхода возвращает балансы; повторное сторно отклоняется; журнал денег и аудит неизменяемы; корректировка требует причину.
**Безопасность:** у `anon` нет доступа к `products.cost_price`, приватным таблицам и RPC; RLS на всех новых таблицах; рассылки выключены по умолчанию, идут только с согласием, есть пауза между рассылками; дедупликация очереди; проверка возраста при выдаче (по настройке); смена режима города не создаёт искусственных долгов и не меняет историю.

## Параллельность (вручную, две сессии)
Автоматический тест в одной транзакции не может проверить гонки. Проверьте на тестовой базе в двух окнах SQL (две отдельные сессии). `OWNER` — ваш Telegram ID.

**A. Двойная выдача одного заказа.** Подготовьте заказ `X` в статусе `prepared`.
* Сессия 1: `begin; select change_order_status('X','issued',OWNER);` (не завершайте).
* Сессия 2: `select change_order_status('X','issued',OWNER);` — зависнет (блокировка заказа).
* Сессия 1: `commit;` — сессия 2 вернёт `bad_transition`.
* Проверка: `select sum(quantity) from batch_consumptions where order_id='X';` = количество в заказе (не вдвое больше).

**B. Два заказа на последние единицы.** Остаток 5, два заказа по 5 оформить нельзя уже на этапе резерва: сессия 1 `begin; select create_order(...5...);` — сессия 2 тот же `create_order` на другой заказ: ждёт блокировку строки склада; после `commit` сессии 1 получает `insufficient_stock`. Проверьте `reserved_quantity <= quantity`.

**C. Одновременное списание с одной позиции.** Два разных подготовленных заказа на одну позицию: в сессии 1 `begin; select change_order_status('X1','issued',OWNER);`, в сессии 2 `select change_order_status('X2','issued',OWNER);` — сессия 2 ждёт и после `commit` списывает из корректного остатка партий. Проверьте `select * from inventory_batch_check(OWNER)` — пусто.

**D. Отрицательный баланс.** На счёте 100 €. Сессия 1: `begin; select account_transfer(OWNER, ACC, ACC2, 60, 'a', 'conc-key-0001');`. Сессия 2: `select account_transfer(OWNER, ACC, ACC2, 60, 'b', 'conc-key-0002');` — ждёт блокировку счёта; после `commit` сессии 1 получает `insufficient_funds`. Баланс не ниже нуля.

**E. Один и тот же ключ.** Две сессии с одним `p_key` для `account_transfer`/`finance_post_entry`/`record_cash_transfer`: вторая получает `duplicate: true`, деньги списаны один раз.

Если какой-то сценарий ведёт себя иначе — это дефект блокировок; приложите вывод.
