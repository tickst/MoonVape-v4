# MoonVape v4 — безопасное обновление Supabase, Render, Vercel

**Главное правило: ни одна из миграций 0019–0025 ни разу не выполнялась на PostgreSQL.** Поэтому сначала — отдельная тестовая база, и только потом — продакшен. Автор изменений не подключался к вашей базе и не запускал ничего на реальных данных.

## 0. Что нужно знать до начала
* Миграции v4 идут строго по порядку после 0018. Каждая начинается с проверки, что предыдущая применена, и записывает себя в `schema_migrations`. Повторный запуск запрещён самой миграцией.
* Миграции **необратимы** (откат = восстановление из резервной копии). Они не удаляют таблицы и данные, но замораживают `cash_transfers` (остаётся для чтения) и удаляют 7-аргументную `finance_post_entry` (заменена версией со счётом).
* Миграция 0021 фиксирует стартовый остаток кассы Hannover **на момент запуска** (= текущая задолженность). Запускайте её, когда никто не выдаёт заказы (несколько секунд).
* Порядок выкладки: **база → backend (Render) → frontend (Vercel)**. Между шагами часть функций временно недоступна (см. таблицу в п. 5).

## 1. Проверить, что уже применено на продакшене
```sql
select version from schema_migrations order by version;   -- должна быть 0018 (и всё до неё)
```
Если последней стоит не 0018 — сначала примените недостающие миграции по `README.md`, раздел 2. Не пропускайте шаги.

Запишите «до» (понадобится для сверки):
```sql
select _settlement('hannover')  as hannover_before, _settlement('muenchen') as muenchen_before;
select count(*) orders, sum(total) total from orders;
select count(*) entries, sum(amount) amount from finance_entries;
select count(*), sum(quantity) from inventory;
```

## 2. Резервная копия и тестовая база
1. Supabase → Database → Backups: сделайте копию (или `pg_dump`). Убедитесь, что её можно восстановить.
2. Создайте **отдельный проект Supabase** (бесплатного достаточно), восстановите в него копию продакшена (или прогоните `schema.sql` + миграции 0002–0018 на пустой базе).
3. В тестовом проекте выполните по очереди (отдельный Run на каждый файл): `0019` → `0020` → `0021` → `0022` → `0023` → `0024` → `0025`.
4. Выполните `supabase/tests_v6.sql`. Ожидаемый результат — сообщение **`ALL V6 TESTS PASSED`**. Любая ошибка: ничего не сохраняется (rollback), текст ошибки указывает проверку. **Не выкатывайте на продакшен, пока тест не пройден.** Если тест упал — пришлите текст ошибки: файлы не запускались, и вероятность хотя бы одной опечатки в ~2300 строках нового SQL высока.
5. В тестовом проекте поднимите backend и frontend (отдельные сервисы или локально) и пройдите чек-лист из п. 6.

## 3. Продакшен: миграции
1. Предупредите администраторов; выберите время без выдачи заказов.
2. Свежая резервная копия.
3. SQL Editor → по одному файлу, каждый — отдельным **Run**: `0019`, `0020`, `0021`, `0022`, `0023`, `0024`, `0025`. После каждого проверьте, что нет ошибки и `select max(version) from schema_migrations` вырос.
4. Сверка после **0021** (деньги Hannover не должны «прыгнуть»):
   ```sql
   select _settlement('hannover')->>'owed' as hannover_after;      -- = hannover_before.owed из п. 1
   select _settlement('muenchen')->>'owed' as muenchen_owed;       -- 0, mode = owner_operated
   select id, name, kind, city_id, opening_balance, _account_balance(id) from cash_accounts order by id;
   ```
5. Сверка после **0022**:
   ```sql
   select i.id, i.quantity, coalesce(s.q,0) batches from inventory i
     left join (select inventory_id, sum(qty_remaining) q from stock_batches group by 1) s on s.inventory_id=i.id
     where i.quantity <> coalesce(s.q,0);                              -- должно быть пусто
   ```
6. Повторите запросы «до» из п. 1: количество и суммы заказов и финансовых записей **не изменились**.
7. **`tests_v6.sql` на продакшене не запускать.**

## 4. Backend (Render)
* Переменные окружения **не меняются**. Новые файлы: `backend/helpers.py` (деплоится вместе с `main.py`). Зависимости (`requirements.txt`) не менялись.
* После деплоя: `GET /health`, затем в админке — «Клиенты», «Финансы → Счета».
* Если надо заранее проверить логику без деплоя: `./scripts/run_checks.sh` (не требует БД/сети), и `pytest backend/tests` (нужны установленные зависимости).

## 5. Что происходит между шагами выкладки
| Состояние | Что работает | Что временно не работает |
|---|---|---|
| База v4 + backend v3 | заказы, бот, статусы, остатки | предпросмотр цены без персональных цен (уже без себестоимости), проводки финансов (`finance_post_entry` 7 арг. удалена) |
| База v4 + backend v4 + frontend v3 | всё серверное | новых разделов в интерфейсе нет; старый «Взаиморасчёты» покажет новые поля без деталей |
| Всё v4 | всё | — |

Telegram-бот и создание заказов работают на каждом шаге.

## 6. Чек-лист после выкладки (вручную, в тестовом проекте, затем в продакшене)
1. Покупатель: открыть каталог, добавить товар в корзину, оформить заказ. Себестоимости в ответах `/api/pricing/preview` нет.
2. Владелец: «Клиенты» → открыть клиента → «Добавить» персональную цену → у клиента в корзине цена с пометкой «персональная цена»; у другого клиента цена обычная.
3. Заказ клиента с персональной ценой: у владельца отмечено 💎, у администратора Hannover — только итоговые цены.
4. «Взаиморасчёты»: München — «управляется владельцем. Передача денег владельцу не требуется»; Hannover — долг, как до миграции.
5. «Финансы → Счета»: введите начальные остатки (кнопка «Корректировка», с причиной): касса München (реальные деньги в кассе), банк владельца.
6. Оформите тестовую закупку на 1–2 позиции (черновик → провести). Выдайте тестовый заказ: себестоимость в «Аналитика → Товары» берётся из партии.
7. Тестовое перемещение München → Hannover: отправить → получить; «Аналитика → Остатки»: стоимость не изменилась.
8. «Настройки → Оповещения»: рассылки **выключены**. Не включайте до юридической проверки (`docs/LEGAL_CHECKLIST.md`).
9. `GET /api/admin/stock/check` (или «Аналитика → Остатки») — расхождений партий нет.

## 7. Откат
* База: только восстановление из резервной копии (миграции необратимы). Если после миграций уже были заказы/операции — откат их потеряет; поэтому тестируйте до продакшена.
* Код: backend и frontend можно вернуть к предыдущему релизу на Render/Vercel, но v3-код не знает про `finance_post_entry` с 8 параметрами и режим города — финансовые операции v3 с базой v4 не работают. Практически откат v4 = восстановление базы + возврат кода.

## 8. Типичные ошибки при запуске
* `run 0018 first` / `run 00NN first` — применяйте строго по порядку.
* `migration 00NN already applied` — миграция уже применена; повторно не запускать.
* Ошибка прав на `revoke ... from anon` — убедитесь, что запускаете в Supabase SQL Editor под владельцем (роль `postgres`).
